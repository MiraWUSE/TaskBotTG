# Telegram-бот для задач и напоминаний

Личный список задач в Telegram с русским интерфейсом, часовыми поясами и фоновыми уведомлениями. Напоминания хранятся в SQLite и продолжают работать после перезапуска. Стек: Python 3.11–3.14, aiogram 3, aiosqlite, asyncio, python-dotenv, zoneinfo; для Windows и минимальных контейнеров установлена база поясов tzdata.

Настройки приложения на Bot-Hosting.net, продление Free и резервные копии описаны в [DEPLOYMENT.md](DEPLOYMENT.md). Перед локальным запуском с тем же токеном остановите серверную копию.

## Возможности

- Создание задачи через пошаговый диалог: название, дата и время, тип повтора.
- Быстрый выбор: через 15/30 минут, через час, сегодня, завтра; гибкий ручной ввод, например `24.10.2026 8:00` или `завтра в 8`.
- Повторы: однократно, ежедневно, по будням, еженедельно.
- Список с пагинацией, задачи на сегодня, карточка задачи, изменение названия и времени, выполнение и удаление.
- В уведомлении: «Выполнено», «Отложить» и «Удалить». Перенос на 10/30 минут, час или другое время.
- Завершение отдельного напоминания не останавливает повторяющуюся серию; для серии есть отдельное действие остановки.
- Настройки личного IANA-пояса, например `Europe/Moscow` или `Europe/Helsinki`.
- Создание одним сообщением с подтверждением, три приоритета, категории и фильтры.
- Несколько предварительных уведомлений на задачу: за 5/15/30 минут, час или день.
- Восстановление пропущенных уведомлений, повторные попытки при ошибках Telegram, защита от доступа к чужим задачам.
- Запуск локально или в Docker Compose, отдельная команда согласованного резервного копирования SQLite.

Бот работает в личной переписке. Публичный адрес, открытый порт и webhook для запуска не нужны: используется long polling. Нужен исходящий HTTPS-доступ к Telegram и корректные системные часы.

## 1. Создайте бота и получите токен

1. Откройте официальный [@BotFather](https://t.me/BotFather) в Telegram.
2. Отправьте `/newbot`, задайте отображаемое имя и уникальный username, заканчивающийся на `bot`.
3. BotFather выдаст токен доступа. Скопируйте его только в локальный `.env`, как описано ниже.
4. Откройте созданного бота и отправьте `/start` после запуска приложения.

Токен даёт управление ботом. Не публикуйте `.env` и не отправляйте токен в исходный код, сообщения об ошибках или репозиторий. Если токен раскрыт, перевыпустите его через `/revoke` у BotFather. Команды меню Telegram приложение регистрирует при запуске.

## 2. Первый запуск на Windows (PowerShell)

Установите Python 3.11–3.14 с [python.org](https://www.python.org/downloads/) и откройте PowerShell в каталоге проекта. Далее используются команды без активации окружения, поэтому менять ExecutionPolicy не требуется.

```powershell
git clone https://github.com/MiraWUSE/TaskBotTG.git
Set-Location TaskBotTG
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
Copy-Item .env.example .env
notepad .env
```

Если установлена другая поддерживаемая версия Python, замените `py -3.12` на её номер, например `py -3.11`. В `.env` замените `PASTE_BOTFATHER_TOKEN_HERE` на токен и сохраните файл. Для обычной работы без тестов достаточно `requirements.txt` вместо `requirements-dev.txt`.

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m bot.main
```

Оставьте терминал открытым. В Telegram отправьте боту `/start`. Для остановки нажмите `Ctrl+C`. Для следующего запуска повторите только последнюю команду. База создаётся автоматически при первом запуске в `data/bot.sqlite3`.

## 3. Первый запуск на Linux

Требуется Python 3.11–3.14 с модулем `venv`. На Debian/Ubuntu пакет для виртуальных окружений обычно называется `python3-venv`; устанавливайте его для используемой версии Python.

```bash
git clone https://github.com/MiraWUSE/TaskBotTG.git
cd TaskBotTG
python3 --version
python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -r requirements-dev.txt
cp .env.example .env
nano .env
chmod 600 .env
```

Вставьте токен в `BOT_TOKEN` и сохраните файл. Если не планируете запускать тесты, используйте `requirements.txt`.

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m bot.main
```

Остановка — `Ctrl+C`, повторный запуск — `.venv/bin/python -m bot.main`. Запускайте команды из корня проекта. Для постоянной работы на сервере используйте Docker Compose из следующего раздела.

## 4. Настройки `.env`

Переменные, уже заданные в окружении процесса, имеют приоритет над `.env`.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `BOT_TOKEN` | Обязательна | Настоящий токен от BotFather |
| `BOT_TIMEZONE` | `Europe/Moscow` | Начальный часовой пояс новых пользователей |
| `DATABASE_PATH` | `data/bot.sqlite3` | Путь к SQLite относительно текущего каталога или абсолютный путь |
| `REMINDER_POLL_SECONDS` | `5` | Интервал проверки наступивших напоминаний в секундах |
| `REMINDER_LEASE_SECONDS` | `120` | Срок резервирования отправки в секундах; должен превышать таймаут Telegram |
| `TELEGRAM_TIMEOUT_SECONDS` | `30` | Таймаут запроса к Telegram в секундах |
| `LOG_LEVEL` | `INFO` | Уровень журналирования |

В Docker Compose путь к базе всегда `/app/data/bot.sqlite3` внутри постоянного тома. Значение `DATABASE_PATH` из `.env` при таком запуске переопределяется в `compose.yaml`.

Без токена, с некорректной конфигурацией или неизвестным часовым поясом приложение завершает запуск с понятной ошибкой. Автоматическим тестам и команде резервного копирования токен не нужен.

## 5. Запуск через Docker Compose

Установите Docker Engine с плагином Compose на сервере либо Docker Desktop на Windows/Linux. Docker должен быть запущен. Скопируйте проект на сервер и выполните из его корня:

```bash
cp .env.example .env
nano .env
docker compose up -d --build
docker compose logs -f --tail=100 bot
```

На Windows вместо первых двух команд используйте `Copy-Item .env.example .env` и `notepad .env`. В `.env` обязательно вставьте настоящий токен перед `up`. `Ctrl+C` при просмотре `logs -f` завершает просмотр логов; контейнер продолжает работать.

Контейнер работает от пользователя `bot` без root. Именованный том `bot_data` хранит базу в `/app/data` и сохраняется при пересоздании контейнера. Политика `restart: unless-stopped` поднимает контейнер после сбоя или перезапуска Docker, если вы не остановили его вручную. Для запуска после перезагрузки сервера сам Docker также должен запускаться автоматически.

В `compose.yaml` на корректное завершение выделено `stop_grace_period: 90s`, что рассчитано на таймаут Telegram по умолчанию 30 секунд. При остановке приложение дожидается активных обработчиков и фоновой отправки перед закрытием базы. Если увеличиваете `TELEGRAM_TIMEOUT_SECONDS`, одновременно увеличьте `REMINDER_LEASE_SECONDS` и `stop_grace_period`: срок остановки должен быть не меньше двух таймаутов Telegram плюс 25 секунд запаса.

Управление:

```bash
docker compose ps
docker compose logs --tail=100 bot
docker compose stop
docker compose start
docker compose restart bot
```

Чтобы применить обновлённый код или зависимости:

```bash
docker compose up -d --build
```

После изменения `.env` пересоздайте контейнер:

```bash
docker compose up -d --force-recreate
```

`docker compose down` останавливает и удаляет контейнер, сохраняя именованный том. **`docker compose down -v` удаляет том вместе с задачами** — используйте эту команду только при намеренном полном удалении данных.

Запускайте одну копию приложения на один токен. Не запускайте одновременно локальный процесс и контейнер с тем же токеном и не масштабируйте polling-сервис. Для другого независимого бота нужны отдельные токен и база.

## 6. Использование

Задачу можно отправить одним сообщением: `Завтра в 15:00 сходить в магазин`, `Через 30 минут проверить почту`, `Послезавтра в 9 утра позвонить другу` или `В понедельник в 8:00 тренировка`. Ближайший указанный день недели выбирается в личном поясе; если сегодняшнее время прошло — через неделю. Поддерживаются числовые даты существующего формата и время в 24-часовом виде, а также слова «утра», «дня», «вечера», «ночи» для 12-часовой записи. Бот показывает точную дату, название и кнопки «Сохранить», «Изменить», «Отмена»; до подтверждения задача не записывается. При отсутствии даты/времени или года бот просит уточнение. Обычный текст не превращается в задачу, активный пошаговый диалог сохраняет своё поведение. Разбор локальный, без ИИ и внешних API.

| Команда | Действие |
|---|---|
| `/start` | Главное меню |
| `/new` | Создать задачу |
| `/tasks` | Актуальные задачи |
| `/today` | Задачи на сегодня в вашем часовом поясе |
| `/settings` | Просмотр и изменение часового пояса |
| `/help` | Справка |
| `/cancel` | Отмена текущего диалога |

Главное меню содержит кнопки «➕ Создать задачу», «📋 Мои задачи», «📅 Задачи на сегодня», «⚙️ Настройки», «❓ Помощь».

Для первого напоминания нажмите «Создать задачу», введите название, выберите «Через 15 минут» и однократный повтор. В карточке задачи доступны изменение, выполнение и удаление. После действий кнопки и текст карточки обновляются; устаревшие кнопки не дают доступ к чужим задачам.

Дату и время можно отправить одним сообщением, например `24.10.2026 8:00` или `завтра в 8`. Можно сначала отправить только дату, а затем ответить на вопрос о времени. Эти же правила действуют при изменении даты задачи и ручном переносе напоминания.

| Что вводить | Поддерживаемые примеры |
|---|---|
| Дата | `24.10.2026`, `4.1.2027`, `24/10/2026`, `24-10-2026`, `2026-10-24` |
| Относительная дата | `сегодня`, `завтра`, `послезавтра` — в личном часовом поясе; регистр букв любой |
| Время после выбора даты | `8` → 08:00, `8:00` → 08:00, `8:5` → 08:05, `8.30` → 08:30, `08:30` → 08:30 |
| Дата вместе со временем | `24.10.2026 8:00`, `24/10/2026 в 8.30`, `2026-10-24T08:00`, `завтра в 8`, `послезавтра 9:15` |

В числовой дате год обязателен и содержит четыре цифры. При записи дня первым день и месяц могут состоять из одной или двух цифр, разделители должны совпадать. Для ISO-записи используется `ГГГГ-ММ-ДД`. Пробелы между датой и временем и вокруг `:`/`.` допустимы.

После точки у времени нужны ровно две цифры минут: `8.05` означает 08:05, а `8.5` отклоняется; вместо него можно написать `8:5`. Часы указываются от 0 до 23, минуты — от 0 до 59, без секунд и AM/PM. На шаге отдельного времени бот ждёт только время; чтобы сменить дату, нажмите «📆 Ввести дату и время».

Несуществующие даты, прошедшее время и время в пропуске при переводе часов отклоняются с понятной подсказкой. Например, `сегодня 8` не переносится автоматически на завтра, если 08:00 уже прошло.

Для повтора выберите ежедневный, будний или еженедельный режим при создании. Еженедельный повтор привязан к дню недели первой даты, будний — к понедельнику–пятнице; первая дата буднего повтора также должна быть рабочим днём. «Выполнено» и «Удалить» в уведомлении относятся к отдельному наступившему напоминанию, а остановка всей серии выполняется в `/tasks`. Перенос конкретного напоминания также сохраняет дальнейшее расписание серии.

## 7. Часовые пояса и повторы

В карточке задачи кнопка «🚦 Приоритет» задаёт высокий 🔴, средний 🟡 или низкий 🟢 уровень; по умолчанию используется средний, в том числе у задач старой базы. Приоритет виден в списке, карточке и уведомлении, распространяется на всю повторяющуюся серию и не меняет время доставки. В списке можно переключить сортировку по ближайшему времени или по важности (внутри уровня — по времени). Выбор сортировки сохраняется отдельно для каждого пользователя.

Кнопка «🗂 Категория» в карточке назначает «Учёба», «Работа», «Личное», «Покупки» или «Другое». Новые и старые задачи по умолчанию относятся к «Другому»: создание не требует лишнего шага. В списке кнопка «Категории» фильтрует задачи, включая список на сегодня; «Все категории» снимает фильтр. Фильтр сохраняется для пользователя и сочетается с сортировкой и пагинацией. Каталог хранится в отдельной таблице `categories` с необязательным владельцем, поэтому будущие личные категории не потребуют замены модели; интерфейс их создания пока не реализован. Доступность категории проверяется сервисом перед назначением и фильтрацией.

Ввод трактуется в личном часовом поясе пользователя, а даты в базе хранятся в UTC. `/today` определяет границы сегодняшнего дня именно в личном поясе, включая дни перехода на летнее время.

Повторы рассчитываются по местному времени в поясе, выбранном при создании серии: ежедневное напоминание на 09:00 сохраняет 09:00 при переходе на летнее/зимнее время. Время, отсутствующее из-за перевода часов вперёд, нельзя ввести вручную; в повторяющемся расписании такая дата пропускается. Для двусмысленного времени при переводе часов назад выбирается первое вхождение, второе уведомление за этот день не создаётся.

Изменение личного пояса меняет отображение уже запланированных задач, сохраняя их моменты UTC; существующие серии сохраняют прежний пояс расписания. Новые даты интерпретируются в новом личном поясе. Явное изменение даты/времени существующей серии заново привязывает её расписание к текущему личному поясу; также можно остановить серию и создать новую.

Если приложение было выключено, оно обрабатывает просроченные задачи после запуска. Для серии создаётся одно пропущенное напоминание и рассчитывается следующая будущая дата: многодневный простой не вызывает поток уведомлений за каждый прошедший день.

## 8. SQLite и надёжность доставки

### Предварительные уведомления

В карточке задачи нажмите «⏳ Напомнить заранее», отметьте один или несколько интервалов (5, 15, 30, 60, 1440 минут) и сохраните. По умолчанию они выключены; «Без предварительного уведомления» снимает выбор, а «Отмена» оставляет прежнюю настройку. Основное напоминание всегда сохраняется.

Сообщение «⏳ Скоро задача!» показывает оставшееся время и дату в личном поясе. У него есть только переход к карточке, без выполнения и переноса: это отдельный вид доставки `advance`, который не завершает задачу и не подменяет основную доставку `main`. Для каждого экземпляра серии и выбранного интервала ведётся собственная запись с lease, попытками и результатом отправки. Уже отправленные записи повторно не создаются. Известное ограничение неопределённого ответа Telegram API описано ниже.

При назначении интервалов или изменении времени прошедшие интервалы не догоняются. После простоя ранее запланированное предупреждение может прийти с опозданием, пока основное время ещё впереди; после наступления срока устаревшее предупреждение отменяется, а основное напоминание доставляется обычным способом. Перенос всей задачи отменяет старые доставки и начинает новое поколение расписания. У повторов интервалы действуют на будущие экземпляры с сохранением местного времени; предварительно готовится и следующий экземпляр, чтобы учесть 23-часовой день при DST.

Завершение или остановка задачи отменяет её ожидающие предупреждения. Отложенное однократное напоминание получает только ещё будущие интервалы относительно нового срока; перенос отдельного уже наступившего экземпляра серии сохраняет предварительные уведомления регулярного расписания и не создаёт для этого экземпляра ещё один набор предупреждений.

### Где что хранится

| Данные | Место хранения | Попадают в GitHub |
|---|---|---|
| Исходники, тесты, инструкции, шаблон настроек | Этот репозиторий | Да |
| Токен и настройки локального запуска | `.env` в корне проекта | Нет |
| Токен серверного запуска | Секретная переменная `BOT_TOKEN` в панели хостинга | Нет |
| Пользователи, задачи и доставки | SQLite `data/bot.sqlite3` по умолчанию | Нет |
| Рабочая база на Bot-Hosting.net | `/home/container/data/bot.sqlite3` | Нет |
| Рабочая база Docker Compose | `/app/data/bot.sqlite3` в постоянном томе `bot_data` | Нет |
| Резервные копии | Путь, указанный в `bot.backup --output`; храните копию вне сервера | Нет |
| Незавершённые шаги диалога | Оперативная память процесса, aiogram MemoryStorage | Нет; теряются при перезапуске |
| Базы автоматических тестов | Временные каталоги pytest | Нет |

Локальная база и серверная база — независимые файлы: автоматической синхронизации между ними нет. После переноса актуальные задачи находятся в базе работающего серверного процесса. Клонирование репозитория не восстанавливает личные задачи; для переноса нужна отдельная резервная копия. GitHub хранит код, но сам не запускает бота. Отправка изменений в GitHub не обновляет действующее приложение: порядок обновления описан в [DEPLOYMENT.md](DEPLOYMENT.md).

| Таблица | Содержимое |
|---|---|
| `users` | Telegram ID пользователя и чата, личный часовой пояс, блокировка бота, сортировка, фильтр категории, время создания и изменения |
| `tasks` | Владелец, название, время UTC, повтор, пояс расписания, приоритет, категория, граница начала предварительных уведомлений, статус `active/completed/deleted`, версии `generation` и `revision` |
| `categories` | Каталог категорий: стабильный ключ, название и необязательный владелец; стандартные доступны всем |
| `task_advances` | Выбранные интервалы предварительных уведомлений для каждой задачи |
| `deliveries` | Задача и поколение расписания, тип `main/advance`, интервал, исходное и фактическое время отправки, статус `pending/sending/sent/completed/cancelled`, попытки, lease, идентификатор сообщения и последняя ошибка |

Временные отметки сохраняются целыми Unix-секундами в UTC. `generation` отделяет новое расписание от старых доставок после изменения даты; `revision` защищает от действий по устаревшим кнопкам. Уникальность `(task_id, generation, scheduled_at, kind, offset_minutes)` предотвращает повторное создание одной записи доставки. Выполненные и удалённые задачи меняют статус, а не физически исчезают из SQLite. База содержит личные данные и не шифруется приложением: доступ к файлу и резервным копиям ограничивается средствами сервера.

База содержит пользователей, задачи, состояния повторов и записи о доставке. Она создаётся и подготавливается автоматически; отдельный сервер SQLite не требуется. Режим WAL позволяет выполнять чтение и запись без длительной блокировки друг друга. Не размещайте рабочую SQLite на сетевом диске.

Схема версионируется через `PRAGMA user_version`; последовательность изменений находится в `bot/database/migrations.py`. Все ожидающие миграции выполняются в одной транзакции вместе с номером версии: ошибка или прерывание откатывает изменения. Перед обновлением существующей базы создаётся проверенная копия в `backups/` рядом с SQLite. Если копирование не удалось, запуск останавливается до изменения схемы. Новая база создаётся сразу до текущей версии. Более новая или неизвестная неверсионированная схема отклоняется.

Текущая версия схемы — **4**: v1 — исходные задачи/пользователи/доставки; v2 — приоритет и сортировка; v3 — категории и фильтр; v4 — интервалы и разделение доставок. При обновлении v4 таблица доставок переносится транзакционно с сохранением старых ID, статусов, попыток, lease и Telegram message ID; прежние доставки становятся `main`, предварительные по умолчанию выключены.

Перед отправкой обработчик атомарно резервирует доставку на ограниченное время. После успешного ответа Telegram результат фиксируется в базе, а после аварийного перезапуска истёкшее резервирование может быть взято повторно. При обычной работе уже доставленные напоминания не отправляются снова. Изменение, выполнение и отмена проверяются перед отправкой, все операции с задачами ограничены Telegram ID владельца.

Для временных ошибок применяются повторные попытки с увеличением задержки от 30 секунд до часа. Для Telegram `RetryAfter` учитывается указанный сервером срок. Ошибка одного адресата не останавливает обработку остальных. Если пользователь заблокировал бота, отправки ему приостанавливаются; после разблокировки отправьте боту личную команду, например `/start`, чтобы возобновить работу.

Telegram не предоставляет ключ идемпотентности для `sendMessage`. Если Telegram принял сообщение, но ответ потерялся, либо процесс завершился между приёмом ответа и записью результата в SQLite, повторная попытка может дать дубль. Гарантировать строго одну доставку в таких случаях невозможно. Резервирования и сохранённые статусы уменьшают вероятность повторов, сохраняя возможность восстановить пропущенную доставку.

Созданные задачи, настройки и доставки переживают перезапуск. Незавершённые диалоги FSM хранятся в памяти: после перезапуска начните создание или редактирование заново, сохранённые задачи остаются в базе.

## 9. Резервная копия SQLite

Для работающего бота используйте SQLite Backup API, а не простое копирование только `.sqlite3`: актуальные транзакции могут находиться в соседнем `-wal`. В проекте есть команда, которая создаёт согласованную копию, проверяет её через `PRAGMA quick_check`, не перезаписывает существующий файл и не создаёт пустую исходную базу при ошибочном пути.

Windows:

```powershell
.\.venv\Scripts\python.exe -m bot.backup --output backups/bot-2026-10-23.sqlite3
```

Linux:

```bash
.venv/bin/python -m bot.backup --output backups/bot-2026-10-23.sqlite3
```

Если база находится в другом месте, добавьте `--database /path/to/bot.sqlite3`. Без этого аргумента используется `DATABASE_PATH` из окружения/`.env`, затем `data/bot.sqlite3`. Выберите новое имя файла для каждой копии. Токен Telegram не нужен, бот может продолжать работать.

Docker Compose:

```bash
docker compose exec bot python -m bot.backup --output /app/data/backups/bot-2026-10-23.sqlite3
```

Скопируйте результат за пределы тома. На Linux:

```bash
mkdir -p backups
docker compose cp bot:/app/data/backups/bot-2026-10-23.sqlite3 ./backups/bot-2026-10-23.sqlite3
```

На Windows каталог создаётся командой `New-Item -ItemType Directory -Force backups`, затем выполняется та же команда `docker compose cp`.

Храните копии отдельно от сервера и не публикуйте их: они содержат пользовательские задачи и Telegram ID. `.env`, `data/`, `backups/` и SQLite-файлы исключены из Git; `.dockerignore` также не допускает их в контекст сборки.

Для восстановления сначала полностью остановите приложение. Сохраните текущую базу отдельной копией, замените рабочую базу проверенным backup-файлом и уберите оставшиеся старые `-wal`/`-shm` именно этой базы при отсутствии всех подключений. Убедитесь, что файл и его каталог доступны на запись пользователю процесса; в Docker это UID/GID `10001`. Затем запустите бота. Не заменяйте SQLite-файл под работающим процессом.

## 10. Автоматические и ручные проверки

Установите `requirements-dev.txt` и запустите:

```bash
python -m pytest -q
python -m compileall -q bot tests
python -m ruff check .
```

Здесь `python` должен быть интерпретатором виртуального окружения; на Windows можно указать `.\.venv\Scripts\python.exe`, на Linux — `.venv/bin/python`.

Тесты используют временные SQLite-базы и подменённую отправку Telegram: реальный токен и сеть не нужны. Проверяются создание/изменение/удаление задач, разные форматы даты и времени, относительные даты и отдельный ввод времени, запрет неверных и прошедших дат, списки и пагинация, переносы, повторы, часовые пояса и DST, восстановление просроченных уведомлений, проверка владельца, повторные попытки, резервирования доставок и online backup с WAL.

Без настоящего токена нельзя подтвердить обмен с живым Telegram, регистрацию команд и внешний вид кнопок в клиенте. После настройки токена проверьте вручную:

1. `/start` и создание короткого напоминания на ближайшую будущую минуту.
2. Получение уведомления без дополнительных сообщений боту; выполнение и перенос.
3. Изменение, удаление, список и `/today`.
4. Личные задачи двух разных Telegram-пользователей и изменение часового пояса.
5. Перезапуск с будущей и просроченной задачей.
6. Ежедневный повтор: выполнение одного уведомления сохраняет серию, остановка серии прекращает будущие уведомления.

## 11. Структура

GitHub Actions (`.github/workflows/checks.yml`) проверяет push и pull request на Python 3.11–3.14: зависимости, синтаксис, критические ошибки Ruff, миграции и полный pytest с предупреждениями как ошибками. Секреты и доступ к серверу не требуются. До публикации ветки workflow можно проверить теми же командами локально; результат GitHub CI появится после отправки изменений.

`bot/main.py` загружает конфигурацию, открывает SQLite, подключает обработчики aiogram и запускает long polling вместе с фоновым обработчиком напоминаний. `handlers/` принимает команды и нажатия, ведёт пошаговый диалог; `keyboards/` формирует меню. `task_service.py` проверяет владельца и меняет задачи в коротких транзакциях `database/db.py`. `datetime_utils.py` разбирает даты и рассчитывает повторы с учётом часовых поясов.

Фоновый `services/reminders.py` периодически выбирает наступившие задачи, создаёт записи доставки, резервирует попытку и обращается к Telegram API. Результат записывается в SQLite; сеть не удерживает транзакцию базы. `lifecycle.py` обеспечивает завершение активных обработчиков до закрытия соединений. `backup.py` отдельно создаёт согласованную копию через SQLite Backup API.

## 12. Если запуск не удался

- **Нет `BOT_TOKEN` / шаблонный токен:** создайте `.env` в корне проекта, вставьте токен и запускайте из этого каталога.
- **`TelegramConflictError`:** остановите второй процесс/контейнер с этим токеном. Если бот прежде работал через webhook, приложение при запуске переключает его на polling.
- **Неверный токен:** получите действующий токен через BotFather и перезапустите процесс; после изменения `.env` в Docker пересоздайте контейнер.
- **Ошибка часового пояса:** используйте IANA-имя с точным написанием, например `Europe/Moscow`; убедитесь, что зависимости установлены полностью.
- **`database is locked` / ошибка записи:** проверьте свободное место, права на каталог базы и отсутствие другого процесса, использующего ту же SQLite. После неожиданного отключения не удаляйте `-wal` у действующей базы.
- **Уведомление задерживается:** проверьте логи, сетевой доступ к Telegram и системные часы. Обычная точность зависит от интервала `REMINDER_POLL_SECONDS`, доступности Telegram и ограничений его API.

Справочные материалы: [Telegram BotFather](https://core.telegram.org/bots/features#botfather), [aiogram](https://docs.aiogram.dev/), [SQLite Backup API в Python](https://docs.python.org/3/library/sqlite3.html#sqlite3.Connection.backup), [Docker Compose](https://docs.docker.com/compose/).
